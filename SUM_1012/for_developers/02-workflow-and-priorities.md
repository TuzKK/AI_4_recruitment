# 详细流程与优化顺序

目标流程如下；箭头表示拟串联的业务关系，不表示已全部实现。

```text
岗位需求与筛选标准
  → 推荐牛人：获取卡片和结构化推荐信息
  → 联系前补充信息：API → DOM → 必要时 OCR
  → 粗筛：依据证据判断是否值得联系
  → 按预算排序、去重、检查联系状态
  → API 自动打招呼并核实结果
  → 按候选人 ID + 职位关联沟通会话
  → 获取详细在线简历 → 清理为 Markdown
  → 依据完整证据独立精筛
  → 分页读取聊天、检查人工接管及重复消息
  → 发送自定义模板／联系方式 → 人工处理
```

## 每一步的现状和需要补齐的内容

| 步骤 | 已有基础 | 待补齐 |
|---|---|---|
| 1. 定义岗位 | 原项目已有岗位要求、硬条件配置和规则评分 | 岗位相关的标准、可核实证据、权重及未知条件处理 |
| 2. 推荐采集 | DOM 卡片已实测；第一个项目另有推荐响应 `_api_profile` 解析 | 验证响应字段覆盖，提取更多工作、项目、技能与求职期望 |
| 3. 联系前补充 | CLI 能自动打开推荐详情，但只有概览 | 定位实际详情请求、嵌入页面、展开与滚动；必要时自动截图 OCR |
| 4. 粗筛 | 规则分 + LLM ±15 分 | 信息不足标为未知，避免编造；优化有限联系额度内的有效候选人比例 |
| 5. 排序与联系 | 第一个项目有打招呼上下文及 API 实现 | 验证正确参数、预算、去重、结果核实；未知结果不得重发 |
| 6. 关联沟通 | 沟通列表读取可用 | 新招呼到会话出现的等待和状态流转；不能按姓名关联 |
| 7. 简历获取与清理 | 已有联系人详细简历和 Markdown 清理已验证 | 新联系人可读条件、缺失模块标记、正式批量导出命令 |
| 8. 精筛 | 第一个项目有二次评估 | 不受初筛 ±15 分限制，解决长文本截断，按岗位证据独立评分 |
| 9. 跟进与交接 | 聊天读取已验证 | 可靠发送、重复检查、拒绝／人工接管状态及人工后续入口 |

关键纠正：目前只能说“沟通读取路径已通过、推荐完整详情未读通”，不能写成“必须打招呼后平台才允许读完整简历”。“新打招呼后立即可读”也未验证。

## 已确认的优化优先级

1. **先拓宽信息获取能力。** 建立字段覆盖清单，对照推荐卡片、详情和沟通简历；API 优先、DOM 补充、OCR 兜底。输出每个字段的来源、缺失和截断情况。
2. **再研究开源匹配项目及模型。** 调研简历与招聘需求匹配的 LLM／监督模型，比较输入要求、语言、许可、部署成本和可复现评测；目前未选型，也未训练。
3. **再改评分与 Prompt。** 粗筛评估联系价值，精筛评估岗位匹配；保留证据、置信度与未知项，使用人工标注样本验证效果，而不是仅把 Prompt 写长。
4. **完成联系与调度闭环。** 将可靠打招呼、会话关联、可读性等待、精筛和消息发送封装为可恢复的 Tools/Workflow。具体交付顺序需结合前面验证结果确定。

## 后台自动化要求与验收

- 正常采集全程由 CLI 发起导航、展开、滚动和截图，无需用户操作业务页面。
- OCR 需要浏览器渲染图像；拟用独立浏览器的截图接口，不依赖桌面截图。无头兼容性、登录态和后台截图均需实测，当前扩展不是已完成的 OCR 实现。
- 登录失效或验证码进入暂停与恢复流程，不能承诺绕过平台验证实现永久无人值守。
- 内容验收分两层：网页／接口是否取得足够内容；取得的内容是否在清理和模型输入中完整保留。分别报告，不能混为一谈。
- 记录每次联系的对象、岗位与结果；超时后先核实，不自动重发。不能根据评分成功就宣称发送成功。

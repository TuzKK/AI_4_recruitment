# 流程、采集与评分优化的详细上下文

本文是需求与设计方向记录，不是已完成实现或最终决策完整的实施计划。用户已经确定先扩充采集能力，再研究匹配模型，最后优化模型与 Prompt；允许 API、DOM 与 OCR 自动补充信息。

## 1. 当前源代码的真实流程

第一个项目从推荐列表获得候选人数据，执行硬条件和规则评分，按配置调用 LLM，再联系符合条件的候选人。另有简历导入与二次评估能力，但不能推导自动取得 BOSS 全文简历已经实现。

`bossmaster.py` 的 `_extract_cards_batch`（约 1761 行）遍历 `[data-geekid]`，输出 `{geek_id,name,text}`，text 为卡片 `innerText`。另有推荐响应解析（约 1863、1929、2047 行）：将 `geekCard` 整理成摘要和 `_api_profile`，含教育、工作、个人摘要等。这一路径值得继续核查其实际返回覆盖，不能笼统描述为该项目“只能读 DOM 卡片”。

`_click_candidate_card_for_detail` 和 `_capture_greet_context_from_list_page`（约 4116、4174 行）打开详情并取得联系上下文，主要提取请求参数，不等于已将详情完整正文送入评分。`send_greeting_with_context`（约 4319 行）调用 `/wapi/zpjob/chat/start`，检查 jid/lid/securityId，并构造 expectId、greet、customGreetingGuide 等参数。它是网页内部接口实现，不是官方开放 API 的证明。

`llm_eval.py` 对初评摘要做空白整理、结构化信息拼接、标签去重及长度限制；教育与工作最多各 5 条，技能标签最多 40 个，初评摘要默认约 4,000 字符。二次简历正文上限 6,000 字符，Prompt 总量另有约 12,000 字符限制，岗位要求和硬条件也可能受裁剪影响。清理和截断是两件事，不能以“clean”名义掩盖正文丢失。

## 2. 当前评分机制及局限

规则分为 `min(100, 25 + 技能[0,50] + 经验[0,15] + 学历[0,10] + 优先项[0,10])`；最终分为 `clamp(规则分 + LLM调整[-15,+15], 0,100)`。第二轮替换第一轮调整，不累加。四维 1～10 分用于展示，不直接加总到最终分。规则已经淘汰的对象不会被 AI 加分救回。

初评 Prompt 要求结构化 JSON、hard_condition_verdict、引用原文的 findings、四维分数及短理由；不确定条件应为 unknown，不应凭推测判 fail。四维是技能深度、经验质量、行业匹配、发展潜力。二评强调项目深度、技术复杂度、量化成果和技能匹配，但仍只返回 ±15 分调整，且带入一次评分结论。

因此不能说源码“没有证据或维度设计”。实际优化问题是：通用维度缺少岗位特定的评分锚点；信息不足时难以可靠排序；规则分主导且模型调整幅度有限；二评可能受初评锚定；长文本截断可能漏证据；没有当前任务的效果评测数据。不能宣称已测得准确率低，也不能凭换模型宣称会提高准确率。

## 3. 拟建设的逐步业务流程

1. 输入岗位需求，拆出职责、必须技能、经验要求和偏好项。后续评分应针对岗位相关证据，不凭姓名或无关个人特征判断适配。
2. 自动进入推荐，获取卡片及当前账号正常可见的推荐响应。保存候选人 ID、职位关联、采集时间、来源和原始内容。
3. 在不发起联系的情况下补充详情。先检查 API 返回，再自动打开／展开／滚动并提取 DOM；文本确实不可提取时才截图 OCR。不能承诺每个渠道都能提供完整简历。
4. 粗筛输出“是否值得联系”及依据，缺失信息单列。把已证实不符合与信息不足区分，不能让模型补写未见经历。
5. 按联系预算排序并去重。具体每日额度、岗位分配、阈值和不确定候选人的处理尚未确定，不应自行填成平台固定限额。
6. 调用真实打招呼能力。发送前验证对象、岗位和所需上下文；发送后核实状态。失败、未知、已联系与成功分别记录；未知结果不能自动重发。
7. 按 ID 与岗位关联沟通会话，等待可读状态。新联系人何时能读详细简历尚未验证，不能把“已点打招呼”等同“完整简历已可用”。
8. 获取详细简历，保留原始响应，清理成统一 Markdown。若字段缺失或读取局部内容，显式标记；不把 MD 当作 PDF 附件。
9. 精筛基于更充分的证据独立评估岗位匹配。记录正文覆盖、评分版本、证据和待核实问题，避免仅在初筛分数上作小幅修正。
10. 对通过精筛的候选人读取聊天历史，检查已有联系、拒绝或人工接管状态，再执行自定义模板／联系方式发送，后续转人工。发送能力尚未可靠实现。

## 4. 采集扩充的技术方向

### API 优先

核查推荐响应、详情响应和沟通简历的字段差异、请求上下文、分页及来源。取页面正常使用的接口和参数，避免把“接口返回成功”视作内容足够。优先利用结构化数据，减少 OCR 的识别误差。

### DOM 补充

由程序自动进入详情、等待、处理 iframe、展开“查看全部”和滚动。保存详情正文而非整个推荐列表；为每个模块记录实际来源及内容范围。空 DOM 可能由加载、嵌入结构或其他渲染方式导致，需诊断后才能选择补救方式。

### OCR 兜底与后台要求

OCR 前必须有浏览器渲染的图像。拟使用独立浏览器进程自动定位简历区域、截图、滚动分段截取、识别及去重，不要求用户截图，也不依赖桌面窗口位置。是否优先无头模式需验证 BOSS 登录与渲染兼容性；有界面但自动化控制的模式可作为候选方案，尚未选定最终部署方式。

不能把当前 Chrome 扩展简单等同于独立后台截图系统。活动标签截图可能影响用户浏览，不作为默认不干扰方案。OCR 输出需要来源和不确定性标记；金额、日期、技能名及重叠段落需要额外核对。登录失效或验证码应暂停并保留进度，不承诺绕过验证。

### 输出与完整性

建议保留原始证据、结构化字段和面向阅读的 Markdown 三层结果。来源、采集时间、模块覆盖与错误单独记录，避免把大量状态字段塞入阅读正文。重复内容按同一字段／经历上下文处理，不应因两个项目描述相似就删除独立经历。

完整性分三层衡量：平台当前账号可见内容是否被取到；清理是否保留取得的正文；送入模型是否覆盖清理结果。每层独立验收。此前 42 项断言仅验证第二层的指定正文，不能作为第一层或模型效果的证据。

## 5. 后续模型研究与评估

用户要求先找开源简历—招聘需求匹配项目、LLM 或监督模型，再决定如何优化。当前没有完成检索、选型、训练或模型调用，不应列出未经调研的“已选模型”。调研应比较中文与技术岗位适配、模型许可、输入上限、证据输出、部署资源、推理成本和可重复评测。

粗筛与精筛不是同一任务：粗筛关注有限联系预算内的有效匹配，精筛关注详细证据下的岗位适配。应构建人工标注的小规模评测集，避免用模型自己的输出当真值；比较卡片输入、扩充输入和详细简历输入带来的增益，并考察漏选、误选、未知条件与证据支持程度。当前没有足够标签来承诺监督微调可行。

## 6. 已确定与待确定的决策

已确定：先采集再模型；API 优先、DOM 补充、OCR 兜底；正常流程无人工业务导航；简历统一 Markdown；最终接入多节点 Workflow 并人工接管后续。

待确定：实际岗位与评测样本、联系额度分配、采集停止条件、后台浏览器部署与登录恢复、OCR 引擎、匹配模型、评分规则、自动发送模板、最终平台宿主。需要基于后续验证与用户选择锁定，不能把本文当作已完成所有决策的施工单。

## 开源项目的实际流程

```text
招聘者账号登录 BOSS 网页，进入推荐牛人
  → 获取推荐列表：DOM 卡片文字 / 推荐响应中的候选人字段
  → 提取基础字段，执行硬条件检查并计算规则分
  → 开启 AI 时：整理摘要 + 岗位要求 + 固定 Prompt
  → 调用用户配置的 LLM，得到调整分、理由等
  → 汇总评分和推荐结果
  → 后续联系流程使用联系参数并执行打招呼
```

实现细节及边界：

1. **DOM 路径读的是 card，不是完整在线简历。** `bossmaster.py:1761` 读取 `[data-geekid]`，输出 `{geek_id, name, text}`，其中 `text` 是卡片 `innerText`。本次实测样本只有卡片文字。
2. 推荐响应解析路径会把 `geekCard` 整理成摘要及 `_api_profile`，含教育、工作等字段，可能比卡片显示丰富，**仍不能保证完整**。入口见 `bossmaster.py:1863、1929、2047`。这不构成 BOSS 提供公开 API 的证据。
3. **已有“打开详情”，但未形成“读取完整详情正文 → AI”的链路。** `bossmaster.py:4173` 附近打开详情并监听响应，主要提取请求 URL 中的 `greet_context` 联系参数；不是把详情正文保存为完整简历送去分析。不要因代码中存在详情监听就宣称已经实现完整在线简历采集。
4. AI 入参会统一空白、整理分段、去重标签、限制经历数量及截断文本；初评摘要默认约 4,000 字符。清洗不等于脱敏，也不能补回未采集到的信息。
5. 匹配采用项目自己的固定 Prompt 和用户配置的模型，不是调用 BOSS 自带 AI 评分。总分由规则分加 LLM 的 −15～+15 调整组成，并限制在 0～100；四维评分不直接加总。
6. 项目另有导入简历及二次评估能力，但不能据此推断会自动取得 BOSS 完整在线简历或聊天附件。二次评估正文仍有 6,000 字符截断；第二次 AI 调整替换第一次，不叠加。
7. 尚未确认自动监听求职者消息、LLM 自动聊天回复、自动下载聊天附件的完整闭环。打招呼和持续自动对话是不同能力。

## 当前效果局限与下一步

用户明确认为仅凭 card 筛选效果很差。其实际问题是输入缺少完整项目经历、职责和成果；修改 Prompt 无法弥补这些缺失。**目前没有效果评测数据，不能把该判断包装成已测得的准确率结论。**

下一步优先验证一位候选人的详情采集：打开账号正常可见的在线简历，读取展开后的正文，或解析页面正常收到的详情响应；与页面逐项对照，记录缺失字段，再决定是否接入二次评估。此步骤尚未实施。可见在线简历不等于附件简历，也不能取得账号无权查看的内容。

详情内容充分后，再考虑“卡片初筛 → 详情复核 → 人工确认联系”的流程。不要先建设完整人才库，也不要把当前项目称为已经打通的自动招聘 Agent。

# BOSS 三层招聘 Workflow：源码与真实账号验证

验证日期：2026-09-29。目标是独立 Workflow＋Tools，不引入 Agent、RAG 或通用节点编辑器。依据本次对话、`docs/handoff.md`、既有源码审计及本轮真实 CLI 调用；没有声称读取其他会话的完整聊天记录。

## 结论

推荐卡片 → 候选人身份关联 → 在线简历 Markdown → 聊天记录的读取链路，已在当前 Chrome 登录账号下实测成功。评分、打招呼、发送消息都有可复用的源码基础，但本轮没有调用外部 LLM，也没有对真实候选人发送消息。因此不能称为三层 Workflow 已完整上线或端到端验收。

## 两个项目的职责

| 项目 | 源码已有能力 | 边界 |
| --- | --- | --- |
| boss-resume-filter | 推荐卡片 DOM/API 摘要采集、规则筛选、LLM 辅助评分、真实打招呼实现、本地简历二次评估 | 原评分不是自由 LLM 总分；在线简历采集未自动闭环；二次正文有 6000 字符截断 |
| BOSS-cli 原版 | 沟通列表、在线简历查询、Markdown 导出、个人聊天记录查询、文本发送接口 | 不是官方 SDK；recruiter greet 仅查询候选人，没有发起招呼；Markdown 字段适配不完整；当前 Windows 认证读取失败 |
| 本轮修改后的 BOSS-cli | 扩展接入现有 Chrome、招聘端状态及接口探测、推荐卡片读取、保留字段的 Markdown、沟通分页、聊天游标 | 写操作默认关闭；发送接口真实可用性、PDF 下载及完整 Workflow 尚未实测 |

## 实际操作与证据

1. 原版认证的进程内及子进程 Cookie 读取均返回 `RequiresAdminError`，inbox 退出码 1。Chrome 已登录并不代表原 CLI 取得了登录态。
2. 用户在现有 Chrome 加载本地扩展后，`browser status --probe` 返回 `connected=true`、`authenticated=true`、`api_readable=true`；招聘职位接口返回列表。
3. `recruiter inbox --page 1 --json` 成功，得到 **164 条沟通关系、159 份候选人详情**。两者数量不相等，后续业务不能按列表顺序或长度强行配对，应按 ID 关联。
4. `browser cards` 成功采集 **37 张推荐卡片**，字段为 `geek_id/name/text`，第一张文字长度 814 字符。仅证明此次页面已加载卡片，不证明全量推荐遍历。
5. 推荐卡片与沟通列表中有 **1 个相同候选人 ID**；该候选人的会话 ID 可从沟通关系和详情关联取得。
6. 对已有会话候选人，`resume`、`resume-download -o -` 成功。返回 **2 段工作经历、3 段项目经历、1 段教育经历**，Markdown 为 18,708 字符，包含候选人和岗位标识。
7. 已对工作和项目中的 11 个较长文本字段进行逐行保留检查，均存在于 Markdown。此检查验证“接口返回 → Markdown”，不是“网页所有可见模块 → 接口返回”的完整性验收。
8. `recruiter chat` 成功返回 **2 条消息**，包括 1 条文本消息和 1 条简历卡片消息，`hasMore=false`。简历卡片不等于 PDF 附件。
9. 在推荐页面上，用交集候选人的 ID 再次关联到已有会话，简历导出和聊天查询均成功。没有重新打招呼，没有发送模板。

真实资料只保存在 `source/boss-cli-main/.runtime/` 中的 `*.private.json`、`*.private.md`，未提交外部 LLM。本报告不复制姓名、聊天正文或联系方式。

## 实测发现的原版导出缺陷

- 真实接口为 `geekProjExpList`，原版读取 `geekProjectExpList`，会漏项目经历。
- 工作正文实际包含 `responsibility`、`workPerformance`，原版仅找 `description/workDesc`。
- 项目正文实际包含 `projectDescription`、`performance`，原版仅找 `description/projectDesc`。
- 数字学历字段可能使字符串拼接报错；同名默认文件可能覆盖；默认第一岗位不能保证属于该候选人。

本轮导出改为保留返回字段和长文本，过滤会话凭证字段；文件名加入候选人/岗位标识摘要，拒绝覆盖已有文件；多岗位场景要求明确指定岗位。完整性依然受账号可见范围和接口返回影响。

## 三个累计层级

### 一级：卡片初筛与打招呼

推荐卡片 → 岗位要求＋Prompt → 原项目评分 → 达标 → 打招呼。

卡片读取已实测。首版评分沿用规则分＋LLM ±15 调整和原有硬条件；自定义维度和权重后续扩展。打招呼复用第一个项目实现，不能把 CLI 原版 greet 当作已发送。

### 二级：在线简历精筛

一级联系成功 → 用 ID 关联沟通会话 → 简历可读 → 导出 Markdown → 二次评分。

不要求先回复；暂不可读则等待。简历读取与导出已实测一位已有会话候选人，不代表新打招呼后马上可读。第二次评分沿用原机制，替换第一次 LLM 调整而非叠加。接入前必须处理原项目 6000 字符截断：本次 18,708 字符的字段保留版 Markdown 不能直接交给原函数后宣称全文已精筛。

### 三级：模板发送与人工接管

精筛通过 → 按会话 ID 读聊天 → 检查重复、拒绝及人工接管 → 填充自定义模板 → 发送一次 → 核实结果 → 人工接管。

聊天读取已实测。姓名用于称呼，不用于唯一匹配。CLI 存在发送接口及进入会话方法，但二者实际前置关系尚未实测，不能凭代码注释断言。未知发送结果不得自动重发。

## 本轮工程交付和未完成项

已修改 CLI，并增加 Chrome 扩展、带令牌的本机只读桥接、账号及文档身份校验、原 Cookie 通道兼容、错误分类、分页参数及导出修复。已创建独立 `.venv` 和启动脚本；连接教程见 `source/boss-cli-main/docs/browser-connection.md`。

截至本报告写入：Python 非线上测试 121 项通过、7 项线上 smoke 未运行；Node 扩展测试 7 项通过。测试使用合成数据；上面的真实调用另行记录。

未完成/未验证：真实打招呼和模板发送、LLM 调用及效果评估、全文评分输入处理、任意新联系人的简历可读条件、完整页面逐项对照、PDF 附件下载、持久化的三层调度与重启去重 Workflow。它们不能由现有读取成功自动推导。

本机服务当前 `allow_writes=false`。进一步发送验证需指定测试对象及消息正文。

## 后续真实发送验证（同日）

用户随后明确授权自行选择已有联系人和礼貌消息。对前述已核对会话，尝试发送一次：

> 您好，方便时想了解一下，您目前是否还在考虑新的工作机会？

执行 `recruiter reply ... --yes --json`，浏览器通道调用原项目 `/wapi/zpchat/fastReply/sendReplyMsg`，参数为 `gid/content`。CLI 退出码 **1**，返回 `invalid_params`，信息为 **“参数错误: 缺少必要参数”**。

随后重新读取聊天历史，仍为原来的 **2 条消息**、消息 ID 未变化，测试文本匹配数 **0**。没有进行猜参数重试，服务已恢复只读。

更新结论：第三层的聊天读取已验证；**原版发送实现按当前参数实测失败，不能直接作为可用的发送 Tool**。需要核实正确发送协议或实现浏览器页面发送适配后，再进行独立验证。本次失败不证明 BOSS 平台本身不能发送，也不证明通过其他实现无法完成第三层。

## 推荐详情与完整性补充验证（2026-09-29）

用户要求正常业务操作全部由代码/CLI 完成，不依赖人工进入某个业务板块。

- 沟通历史：另取已有会话，首批 2 条、hasMore=true；使用最小消息 ID 作为 before 游标读取下一批，新增 2 条、重复 0 条、hasMore=false。两页共 4 条，已到接口历史末尾。该结论不涵盖已删除或平台不返回的消息。证据为 `.runtime/chat-pagination.private.json` 和脱敏摘要 `chat-pagination-summary.json`。
- 沟通在线简历：此前已读取详细经历并导出 18,708 字符 Markdown，11 段工作/项目长文本按行核对保留。尚未对网页所有可见模块逐项核对，因此不能宣称无条件获取所有人的完整在线简历。
- 推荐未沟通候选人：取推荐卡片中未匹配到已获取沟通列表的 ID，直接使用已有岗位参数请求原版简历接口，失败“未知的非法参数”。这说明该参数组合不可用，不证明推荐详情不可读取；也不能仅凭列表未匹配断定从未沟通过。
- 已添加固定目标页面自动导航、按卡片 ID 安全打开详情、读取详情页面正文及该页已发生的简历请求参数。121 项 Python 测试和 8 项 Node 测试通过，相关 Python 模块 Ruff 通过。新命令的线上验证尚未完成。
- 本机只读桥接已重启加载新命令。Chrome 仍运行旧版扩展，实测 `browser navigate recommend` 返回“不支持的命令”。电脑控制工具启动失败（sandbox helper lock），无法代为点击扩展重载；已请求一次性更新重载，未再要求人工打开业务页面。

当前待验证：更新扩展后由 CLI 自动进入推荐、打开未沟通候选人详情，取得其真实请求上下文，再核对接口/网页/Markdown 内容；随后核对沟通简历可见模块。上述未完成项不能记作已通过。

### 扩展更新后的实际结果

用户完成一次性重载与重新连接后，业务操作均由 Python/CLI 调用本地桥接完成，没有再要求人工切换 BOSS 页面，也没有发送消息。

1. 自动从沟通进入推荐成功，读取 15 张当前卡片，按 ID 自动点击其中一张卡片的详情入口成功。
2. 详情快照的 8,426 字符页面正文混有推荐列表，**不是完整简历**。独立简历相关容器只有约 302 字符（含操作文字），其中经历概览约 285 字符；`c-resume` 嵌入页面正文为空。延迟复查结果相同，没有捕获到当前实现指定的 `/wapi/zpjob/view/geek/info` 请求。因而当前 CLI + 本地扩展尚不能证明能读取该推荐候选人的完整在线简历；这不是平台本身不支持查看的结论。证据：`recommend-detail-snapshot.private.json`、`recommend-detail-snapshot-late.private.json`。
3. 自动进入沟通成功，重新读取已有联系人在线简历成功：`friend=true`、`hiddenResume=0`，2 段工作、3 段项目、1 段教育经历，以及专业技能等。导出 18,707 字符 Markdown，按本次大于 60 字符的筛选口径检查 6 个经历长文本字段，所有非空正文行均保留。与先前 11 字段口径不同，不代表字段减少。证据：`communication-resume-recheck.private.json/md`。仍未完成与网页逐项核对，不能保证所有账号/候选人的全部可见内容均可取得。
4. 重新自动循环聊天分页，每次 count=2，共 3 次请求、4 条消息，最终 `hasMore=false`。完成到接口末尾；默认单次 chat 命令本身并不会自动获取所有页，本次使用代码循环。证据：`chat-pagination-recheck.private.json`、`chat-pagination-recheck-summary.json`。

最终结论：推荐卡片和详情入口的自动操作已通过；推荐完整在线简历读取尚未通过。沟通详细在线简历读取与无正文截断导出已通过样本验证；沟通历史自动翻页到接口末尾已通过。完整网页逐项一致性与更广泛候选人覆盖仍未验证。

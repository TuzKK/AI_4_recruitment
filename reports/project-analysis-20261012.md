## 1. 按影响排序的问题

| 优先级 | 问题 | 对业务的影响 | 下一步及验收 |
|---|---|---|---|
| P0 | 联系前只有卡片和概览，推荐全文未读通 | 缺少经历、职责、成果证据，有限联系额度可能消耗在不适配人选上 | 对照相同候选人的 API、DOM 与页面可见模块，输出覆盖与缺失；记录为何停止采集 |
| P0 | 缺失信息在部分规则中被当作不符合 | 稀疏卡片可能过早淘汰好候选人，后续 AI 无法补救 | 必要条件区分满足、不满足、未知；负面结论必须有证据，未知进入补采或复核 |
| P0（启用发送前） | 打招呼、新会话关联、简历可读性和消息发送未贯通 | 不能交付自动招聘闭环，存在错对象、漏联系或重复联系风险 | 在明确授权的测试中逐段核对对象、岗位、结果；成功、失败、未知分别持久化 |

| P1 | 正文与岗位条件可能被截断 | 后段项目、必要条件缺失，模型却可能输出确定结论 | 按模块和实际模型输入预算处理；记录送入/遗漏内容，必要条件优先保留 |
| P1 | 缺少当前岗位人工标注评测集 | 无法判断扩大采集、换模型或改 Prompt 是否有效 | 同一批候选人比较卡片、补充详情、详细简历输入，评估有限预算下的有效人选比例 |
| P1 | 批量抓取、清理和完整分页依赖临时脚本 | 重跑、失败恢复、未知字段处理和运维体验尚未产品化 | 收敛为稳定工具接口，提供进度、断点、错误分类和内容覆盖报告 |
| P2 | 独立后台浏览器、OCR 和宿主未选定 | 技术路线与部署成本不确定 | 先验证必要能力；按登录恢复、后台渲染、可恢复调度与集成成本决定宿主 |

## 2. 本次源码核对发现的具体问题

以下路径均相对固定快照 source/boss-resume-filter-8a150c26f7ef06a90e2ed613fea20d55719b0f75/；这些是参考项目问题，不能直接认定改造后的 BOSS-cli 已采用同样逻辑。

### 2.1 信息缺失与明确不符混淆

filtering.py:803–824 对普通必要关键词及 AND/OR 条件，未命中就返回失败。经验未知则转人工（549–552），说明不同条件的未知处理不统一。

建议将每项条件保存为 verdict、证据、来源与缺失原因。未出现某技能只能说明当前材料未证明，不能直接证明候选人不会该技能。完整性不足时优先补采；只有明确不符才淘汰。

### 2.2 无技能配置时仍可获得技能满分

filtering.py:721–724 在关键词权重总和不大于零时给技能分 50。结合基础分 25，在其他条件允许通过的情况下，即便没有技能证据，也能达到 75 分的“强烈推荐”门槛。

这是静态可推导的配置风险，不代表本项目实际岗位正在使用空配置。建议把未配置标记为配置不完整，自动联系前校验；不要将缺少评价标准解释为技能满分。

### 2.3 经验硬条件文本与解析格式不一致

candidate_scan_policy.py:64 生成“经验：要求≥N年”，llm_eval.py:604 只匹配“经验：≥N年”。该格式差异使对应匹配无法命中，可能削弱 AI 经验不足发现的确定性复核；已有确定性经验初筛仍存在。

建议以结构化规则传递经验阈值，避免生成展示文本后再用正则解析；实施时增加该路径的回归用例。当前仅静态核对，未运行复现测试。

### 2.4 LLM 失败后仍可能进入联系流程

llm_eval.py:1122–1146 保留已有分数并标记错误；bossmaster.py:5678–5681 明确提示 AI 失败本身不阻断联系。若业务认为 AI 是联系前必需环节，这与预期不一致。

建议明确岗位级失败策略：允许规则降级，或暂停该候选人联系。降级必须有显式状态、适用条件和独立阈值，不与完整评估结果混排而不作标记。

### 2.5 二评可能连岗位必要条件都未传入

llm_eval.py:1160–1185 将简历限制到 6,000 字符；总预算不足且岗位要求超预算时，直接将 hard_conditions 置为空。1171–1173 还读取初评分数与理由。1241–1248 仍以规则分加本次调整得到总分。

建议保护必要条件输入预算，再按模块组织简历证据；超限时显式返回输入不完整。精筛重新评估证据与资格，并明确更充分证据如何更新初筛未知或错误结论，不让完整简历仅成为初筛的小幅校正。

源码入口：[filtering.py](../source/boss-resume-filter-8a150c26f7ef06a90e2ed613fea20d55719b0f75/filtering.py)、[llm_eval.py](../source/boss-resume-filter-8a150c26f7ef06a90e2ed613fea20d55719b0f75/llm_eval.py)、[candidate_scan_policy.py](../source/boss-resume-filter-8a150c26f7ef06a90e2ed613fea20d55719b0f75/candidate_scan_policy.py)、[bossmaster.py](../source/boss-resume-filter-8a150c26f7ef06a90e2ed613fea20d55719b0f75/bossmaster.py)。

### 2.6 CLI 名称、发送能力与恢复边界

补充源码核对：BOSS-cli 的 recruiter.py:203 命令描述声称发起沟通，但 214–222 仅调用 get_boss_view_geek 并返回信息。client.py:582–587 的消息发送仍仅提供 gid/content，与历史“缺少必要参数”失败记录吻合；不能因此断定具体缺哪个参数。

browser_bridge.py:42–43 使用内存 pending 和队列，76–83 在超时后移除 pending，101–102 对无法找到的回执返回 False。这意味着服务重启与晚到回执不能仅靠当前桥接恢复，需要业务层持久化动作意图、未知结果及核实流程。50–51 在扩展客户端身份改变时要求重启桥接，重连体验仍有优化空间。

Boss-main 的 backend/rpa/page_actions.py:106/110/114 中聊天读取、发送及附件功能仍抛 NotImplementedError，pipeline/orchestrator.py:339 也标明聊天回复与附件未实现。不能因为其具备 UI 和编排框架，就认为迁入即可补齐闭环。

证据：[recruiter.py](../source/boss-cli-main/boss_cli/commands/recruiter.py)、[client.py](../source/boss-cli-main/boss_cli/client.py)、[browser_bridge.py](../source/boss-cli-main/boss_cli/browser_bridge.py)、[page_actions.py](../source/Boss-main/backend/rpa/page_actions.py)、[orchestrator.py](../source/Boss-main/backend/pipeline/orchestrator.py)。

## 3. 采集优化应如何验收

不要用 Markdown 文件长度、接口成功码或历史测试数量代替内容完整性。当前 42 项正文检查证明指定接口内容在清理后保留，没有证明所有网页模块取得，也没有证明模型看到了这些内容。[证据范围](../SUM_1012/for_AI_references/01-projects-and-evidence.md)

建议建立模块覆盖表：个人介绍、工作、项目、教育、技能、期望；每项记录候选人/岗位 ID、来源、采集时间、可见范围、是否展开、缺失原因、是否截断。缺失至少区分“确认无内容”“未采集到”“当前不可见”“解析失败”，不要全部变成空字符串。

完整性分三层独立验收：

1. 页面或接口 → 原始证据：同一人逐模块对照，重点检查嵌入页面、展开和滚动。
2. 原始证据 → 结构化数据/Markdown：保留取得的正文，未知模块至少保存并提示，不静默丢弃。
3. Markdown/结构化数据 → 模型输入：核对所有关键证据是否进入输入，输出遗漏清单。

API → DOM → OCR 是条件式补充流程，不宜每人无条件全部跑。API/DOM 已满足岗位关键证据需求时停止；空 DOM 先诊断加载、iframe、选择器与渲染，不能直接推导必须 OCR。OCR 需要独立渲染、分段截图、重叠去重及识别不确定性核查，其投入应由实际补充收益决定。[设计依据](../SUM_1012/for_AI_references/02-workflow-and-design-context.md)

## 4. 评分与评测优化

粗筛的目标是“在联系预算 K 内选出值得进一步了解的人”；精筛的目标是“依据详细证据判断岗位匹配”。两者应使用不同结论与评测指标，分数不解释为概率。

建议先针对一个真实岗位建立人工标注集，覆盖通过、拒绝、未知、长简历与跨页经历。可从 30–50 份试点开始，这是实施建议，不是现有成果或充分统计保证。对同一候选人做输入对照，固定岗位和模型设置，再比较：

- Precision@K：前 K 名中人工确认值得联系的比例。
- 漏选：抽查被拒绝者及未知者，不能只标注已联系对象。
- 证据正确性：结论是否有真实原文支撑，是否把缺失误判为不符。
- 运行成本：每份耗时、请求/OCR/模型成本与人工修正时间。
- 联系后收益：详细简历确认匹配率；回复率另列，不能替代岗位匹配质量。

研究开源模型时用相同评测集比较中文岗位、长文本覆盖、证据输出、许可、部署成本；当前不应直接选型或承诺微调收益。先确定评测协议，再进行选型实验。[已有研究需求](../SUM_1012/for_AI_references/02-workflow-and-design-context.md)

## 5. 闭环与恢复机制

建议持久化最小流程状态：发现 → 已采集 → 初筛完成 → 待联系 → 联系待核实/成功/失败 → 等待会话 → 简历就绪 → 精筛完成 → 待跟进 → 已交接。登录失效、验证码、拒绝和人工接管作为可暂停或终止的业务状态。

每个外部动作保存账号、候选人 ID、岗位、动作意图、发送时间、核实证据与结果。跨岗位是否允许再次联系应是显式政策；并发任务需共享预算与发送占用记录。超时表示结果未知，恢复时先核实，不直接重发。人工接管应在实际发送前再次检查，避免队列准备后人工已开始沟通仍继续自动发送。

这些是建议的集成要求，不是断言现有桥接没有安全保护；总结已记载账号身份校验、默认只读及未知结果不重放。缺口是将这些局部保护贯穿到持久化业务流程。[现有保护与未验收范围](../SUM_1012/for_AI_references/01-projects-and-evidence.md)

## 6. 推荐推进顺序与阶段产物

| 阶段 | 交付物 | 进入下一阶段的依据 |
|---|---|---|
| A：采集诊断与字段覆盖 | 推荐 API/DOM 差异、失败原因、可见内容对照与覆盖报告 | 明确哪些字段可取得、哪些需补充；无需人工业务导航 |
| B：最小纵向验证 | 采集→初筛→真实联系→ID/岗位会话关联→简历读取的单条链路 | 在明确授权测试中核实各状态；未知结果可恢复且不重发 |
| C：模型研究与独立精筛 | 人工标注集、输入对照、模型候选比较与证据化评分 | 相对基线的收益与成本可量化，必要条件和关键正文不静默遗漏 |
| D：工具产品化与调度 | 正式批量工具、断点、预算、去重、人工接管、发送核实 | 多次运行和中断恢复不重复外部动作，错误可定位 |
| E：后台部署与宿主集成 | 浏览器恢复、必要的 OCR、最终平台与部署说明 | 依据后台兼容与集成验证选择宿主，再扩展节点编排 |

保留“先扩大采集、再模型、再评分”的主线。与此同时，将发送接口与新会话可读性的可行性验证前移为小规模验证，提前识别闭环硬阻塞；这不意味着在评测之前开展批量自动联系。完整调度、丰富 UI、人才库和训练可在核心链路可靠之后推进。

## 7. 应补齐的决策

真正需要锁定的是：首个岗位与必要条件、联系预算及跨岗位去重政策、信息不足的处理、AI 失败降级策略、采集停止条件、人工接管规则、后台部署方式、最终宿主。模型名称和 OCR 引擎应在证据与评测约束明确后选择。
